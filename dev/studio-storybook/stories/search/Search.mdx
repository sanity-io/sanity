# Search

Search is the only surface in this catalog that is not a component. It is a small application
living inside the navbar: a reducer holding the whole interaction state, a filter engine that
derives itself from the schema at runtime, and a query lifecycle that reaches the Content Lake and
comes back. Around 130 files.

That shape is why the chapter is built the way it is. A screenshot of a search box tells you
nothing about search. So these stories run it.

## The search actually searches

Every result you see in this chapter was found, not seeded. The storybook is backed by a mock
Content Lake: a client whose GROQ queries are evaluated in the browser by `groq-js` against a set
of fixture documents. The query the studio builds is the query that runs. Type something else into
any of these stories and the results change, because there is a real query engine underneath.

## Three things to know before you read the code

<Row title="The filter bar cannot be collapsed in the popover">
  <code>SearchHeader</code> forces <code>filtersVisible</code> back to true whenever{' '}
  <code>!fullscreen</code>. A consequence most people never notice: the instructional empty state
  renders only when <code>!filtersVisible && fullscreen</code>, so search's one piece of onboarding
  copy is unreachable on a wide viewport. It has its own story in the dialog, precisely because it
  is so easy to never see.
</Row>

<Row title="The default search strategy has no offline execution path">
  Studio search ships two strategies. The default, <code>groq2024</code>, searches with{' '}
  <code>text::matchQuery</code> and ranks with <code>score()</code>; <code>groq-js</code> implements
  neither, so it cannot be evaluated locally at all. This chapter therefore runs the documented{' '}
  <code>groqLegacy</code> strategy. Everything these stories demonstrate is identical between the
  two, since both drive the same UI, but hit <em>ordering</em> here is indicative rather than
  production-identical.
</Row>

<Row title="Type narrowing and filters are different axes">
  Narrowing constrains <em>what is searched</em>; a filter constrains <em>which values qualify</em>.
  They are stored separately in the reducer and compile into different parts of the query. Stories
  exist for each on its own so the difference is visible rather than asserted.
</Row>
